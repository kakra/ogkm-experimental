# dmem cgroup accounting in the NVIDIA driver, and what VRAM tools show

- **Status:** code analysis; the live test of the central hypothesis is open
- **Evidence:** `evidence/2026-10-25-vulkaninfo/`
- Sources: open-gpu-kernel-modules 615.78.08 (the series does not touch the
  dmem code), Linux 6.18 `kernel/cgroup/dmem.c`, MangoHud master as of
  2026-10-22.

Background: tools such as dmemcg boosters set `dmem.low` on the cgroup of the
foreground game to protect its VRAM. Users of the NVIDIA driver report
different effects, and overlays such as MangoHud showed a constant ~4 GB of
VRAM use on a 12 GB card in one session. This analysis checks what the driver
actually does with dmem.

## Summary

1. The driver charges every video memory allocation of an RM client to the
   cgroup of the calling task. It does not evict anything itself.
2. `dmem.max` is a hard limit: allocations above it fail with
   `NV_ERR_RESOURCE_ACCOUNTING_HARD_LIMIT_EXCEEDED`.
3. `dmem.min` is the only protection value the driver evaluates. Above it,
   RM sends event 200 (`NV2080_NOTIFIERS_MEMACCT_SOFT_LIMIT_EXCEEDED`) to the
   user-space driver, event 201 when usage drops below it again. The
   allocation succeeds either way.
4. `dmem.low` is ignored: the driver calls
   `dmem_cgroup_state_evict_valuable(..., ignore_low = true)`.
5. Nothing in the open modules listens for events 200/201. The receiver can
   only be the closed user-space driver, which exposes
   `VK_EXT_pageable_device_local_memory` and therefore can move device-local
   memory to sysmem on its own.
6. MangoHud reads `nvmlDeviceGetMemoryInfo().used`, the device-wide usage of
   the driver, not dmem.

## Kernel side (6.18)

`kernel/cgroup/dmem.c` only counts and limits:

- A driver registers a region (`dmem_cgroup_register_region`), visible in
  `/sys/fs/cgroup/dmem.capacity`.
- `dmem_cgroup_try_charge()` charges the cgroup of the current task,
  hierarchically. Above `dmem.max` it returns `-EAGAIN`.
- `dmem_cgroup_state_evict_valuable(limit_pool, test_pool, ignore_low, ...)`
  only answers "may this pool be evicted from": protected up to the effective
  `min`; with `ignore_low == false` also up to `low`; with `ignore_low ==
  true` everything above `min` is evictable.
- Eviction itself is the driver's job. amdgpu and xe do it in TTM. The NVIDIA
  driver does not use TTM, so TTM-level work on dmem protection does not apply
  to it.

## Driver side: memacct (since 610.43.02)

`src/nvidia/src/kernel/mem_mgr/memacct.c`, OS glue in
`kernel-open/nvidia/os-interface.c` and `src/nvidia/arch/nvalloc/unix/src/os.c`.

- **Mode:** `osCgroupImplementation()` picks dmem (`CGROUP_IMPL_OS`) when the
  kernel has the controller, otherwise a misc cgroup fallback or none.
  Registry override `RmMemacctMode` (0 none, 1 fallback, 2 os).
- **Region:** `nvidia/<pci address>/vidmem`, size = total VRAM, registered at
  GPU init (`memacctInitGpuInfo`). What RM, GSP and firmware already use at
  that point is precharged once to the cgroup of the initializing task.
- **Charging:** only in `vidmemConstruct()`, i.e. every video memory
  allocation of an RM client (not with MIG). `memacctTryChargeOs()`:
  - `osMemacctTryCharge` → `dmem_cgroup_try_charge`; failure above
    `dmem.max`, the user-space driver has to fall back itself;
  - if the cgroup is not the root and `osCgroupCanEvict(NULL, pool)` is true,
    the "soft limit" counts as exceeded. `osCgroupCanEvict()` calls
    `dmem_cgroup_state_evict_valuable(NULL, pool, ignore_low = NV_TRUE, NULL)`,
    so **soft limit exceeded ⇔ `dmem.current` > effective `dmem.min`**;
  - then `gpuNotifySubDeviceEvent(..., 200, pid)`.
- **Release:** `memacctReleaseCharge()` sends event 201 when the cgroup goes
  from above to below the soft limit.

### Consequence for `dmem.low` based tools

Without `dmem.min`, the effective minimum is 0, so **every** non-root cgroup
with any VRAM usage is "above its soft limit": the foreground game and every
background application get event 200 on each allocation. Under the NVIDIA
driver, a foreground/background distinction only exists through `dmem.min`
(protection) or `dmem.max` (cap for the background).

## MangoHud

- For vendor `0x10de` only the NVML path is used, no fdinfo
  (`src/gpu.h`).
- `src/nvidia.cpp`: `nvmlDeviceGetMemoryInfo()`; the `vram` element shows
  `used`, device-wide, the same value `nvidia-smi` reports. `proc_vram` comes
  from `nvmlDeviceGetGraphicsRunningProcesses()`. Neither is dmem.

## Observations on the test system

- 2026-10-23: after a reboot into the patched driver, MangoHud showed up to
  12 GB instead of a constant ~4 GB. No patch of the series touches memacct,
  `vidmemConstruct()` or the FB/heap info controls NVML uses. The most likely
  explanation is the reboot itself (fresh memory, failed sysmem allocations of
  the old session gone, per-boot dmem settings reset), not a patch.
- 2026-10-25: dmem is delegated down to the user services. `session.slice`
  with a full Plasma session uses about 1000 MiB (KWin 662, plasmashell 338),
  so a `dmem.max` of 512M there would make KWin's allocations fail.

## Hypothesis and test

Hypothesis (not measured): the user-space driver reacts to event 200 by moving
allocations to sysmem, so with `emin = 0` a game would keep its VRAM working
set small under any non-root cgroup.

Test: the same scene without and with `dmem.min` of about 8G on the game's
cgroup; compare `dmem.current` of the game cgroup, `nvidia-smi` and the
overlay value.

```sh
cat /sys/fs/cgroup/dmem.capacity
CG=/sys/fs/cgroup$(cut -d: -f3 /proc/<game pid>/cgroup)
grep . $CG/dmem.{current,min,low,max}
grep -r . /sys/fs/cgroup --include=dmem.current 2>/dev/null | grep -v ' 0$'
nvidia-smi --query-gpu=memory.used,memory.total --format=csv
```

Open question for the driver: how the user-space driver reacts to events 200
and 201, and whether `dmem.low` support is planned.
